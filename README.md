# ПОС — Преподавательская оценка студентов

**ПОС** — учебное консольное приложение на Go для учёта студентов, критериев оценивания и оценок преподавателя. Приложение рассчитывает итоговый балл по весам критериев и экспортирует ведомость в CSV.

Проект выполнен в рамках домашнего задания № 2 по дисциплине «Конструирование программного обеспечения»: **DDD, слоёная архитектура, паттерны GoF и DI-контейнер**.

## Быстрый старт

Требования: **Go 1.22+**. Сторонняя зависимость — [`go.uber.org/dig`](https://github.com/uber-go/dig) для внедрения зависимостей.

```bash
git clone https://github.com/sadukd/pos.git
cd pos
go run ./cmd/pos
```

Запуск тестов:

```bash
go test ./...
```

Данные хранятся **только в оперативной памяти**. При завершении программы студенты, критерии и оценки не сохраняются; для получения файла с результатами используется команда **Export CSV**.

## Возможности

Приложение предоставляет пять разделов интерактивного меню:

| Раздел | Действия |
| --- | --- |
| **Students** | Просмотреть список, добавить, изменить и удалить студента |
| **Criteria** | Просмотреть критерии, добавить и удалить критерий рубрикатора |
| **Evaluations** | Выставить или заменить оценку, удалить оценку |
| **Results** | Посмотреть подробный результат студента или результаты всех студентов |
| **Export CSV** | Выгрузить ведомость в `./results.csv` |

Для удаления студента, критерия или оценки запрашивается подтверждение `y/n`. Выбор пунктов выполняется числовыми клавишами; в списках доступны переходы `<` и `>`, возврат — `q`. Длинные списки отображаются постранично (по 10 строк).

## Предметная область и DDD

### Единый язык (Ubiquitous Language)

- **Student (студент)** — человек, которому выставляют оценки; имеет идентификатор, ФИО, группу и электронную почту.
- **Criteria (критерий)** — правило оценивания с названием, максимальным баллом (`maxScore`) и весом (`weight`).
- **Rubric (рубрикатор)** — общий для всех студентов набор критериев.
- **Evaluation (оценка)** — балл и необязательный комментарий, выставленные студенту по определённому критерию.
- **StudentEvaluations (оценки студента)** — набор оценок одного студента по критериям рубрикатора.
- **FinalScore (итог)** — вычисляемое значение, зависящее от текущих критериев и выставленных оценок; отдельно не хранится.

### Карта доменной модели

| Элемент | Роль в DDD | Ответственность |
| --- | --- | --- |
| `Student` | Entity, Aggregate Root | Идентичность студента и корректность личных данных |
| `Rubric` | Aggregate Root | Управление составом критериев и уникальностью их названий |
| `Criteria` | Entity внутри `Rubric` | Параметры одного критерия с постоянным ID |
| `StudentEvaluations` | Aggregate Root | Не более одной актуальной оценки по каждому критерию для данного студента |
| `Evaluation` | Доменный объект внутри `StudentEvaluations` | Балл по критерию и комментарий |
| `FullName`, `Email`, `Score` | Value Objects | Проверка корректности и представление значений |
| `ScoreCalculator` | Domain Service | Вычисление итогового балла по стратегии |
| `EvaluationFactory` | Доменная фабрика | Создание оценки только для существующего критерия и в допустимом диапазоне |

**Почему `Student` — Entity, а `Email` — Value Object?** Студент сохраняет идентичность благодаря `StudentID`, даже если его ФИО или email меняются. Email определяется своим значением, не имеет отдельного идентификатора и проверяется при создании.

**Границы агрегатов.** В системе три корня агрегатов: `Student`, `Rubric`, `StudentEvaluations`. `Rubric` контролирует свой набор критериев, `StudentEvaluations` — оценки одного студента, а `Student` — личные данные. Координация действий, затрагивающих несколько агрегатов (например, удаление студента вместе с оценками или запрет удаления используемого критерия), выполняется в Application.

### Доменные инварианты

Доменная модель не позволяет:

1. Создать студента без корректного ФИО, непустой группы или синтаксически допустимого email.
2. Создать критерий с пустым названием, `maxScore <= 0` или весом вне `[0, 1]`; `NaN` и бесконечность также запрещены.
3. Добавить в рубрикатор два критерия с одинаковым названием без учёта регистра и пробелов по краям.
4. Выставить оценку по критерию, которого нет в текущем рубрикаторе.
5. Выставить балл меньше нуля или больше `maxScore` выбранного критерия.
6. Хранить две разные актуальные оценки одного студента по одному критерию: повторное выставление **заменяет** предыдущую оценку и комментарий.
7. Удалить критерий, по которому хотя бы одному студенту уже выставлена оценка. Сначала нужно удалить соответствующие оценки.

При создании критерий получает ID, название, `maxScore` и вес; редактирование этих полей не предусмотрено. Идентификаторы студентов и критериев генерируются автоматически отдельными последовательностями.

Репозитории сохраняют и возвращают **копии агрегатов**. Поэтому изменение загруженного агрегата не изменяет состояние In-memory хранилища до явного `Save()`.

### Расчёт итогового балла

Итог рассчитывает `ScoreCalculator`, использующий `WeightedScoreStrategy`:

\[
\text{FinalScore} = \operatorname{round}\left(\min\left(\sum_{i=1}^{n}\text{Score}_i \cdot \text{Weight}_i,\ 10\right)\right)
\]

- `Score_i` — выставленный балл по критерию (от `0` до его `maxScore`).
- `Weight_i` — вес критерия от `0` до `1`; требование суммы весов, равной единице, **не вводится**.
- Если оценка по критерию отсутствует, в расчёте используется **0**; в интерфейсе и CSV отсутствие отображается как **`N/A`**, чтобы не путать его с выставленным нулём.
- Сумма ограничивается сверху значением **10**, затем округляется до целого по правилам `math.Round`.

Например, при критериях «Домашняя работа» (вес `0.4`) и «Экзамен» (вес `0.6`) оценки `8` и `9` дают `8 × 0.4 + 9 × 0.6 = 8.6`, то есть итог **9**.

Итог **не сохраняется** в качестве независимого поля: он пересчитывается из актуального рубрикатора и оценок, поэтому не может устареть после изменений.

## Архитектура: Clean Architecture

Выбрана **Clean Architecture** с зависимостями, направленными к внутренним слоям:

```text
cmd/pos (composition root, DI)
      │
      ├──> adapters/cli ───────> application ───────> domain
      │                              │                  ▲
      ├──> adapters/repository ──────┴──> ports ───────┘
      │             │
      │             └───────────────────────────────> domain
      └──> adapters/export ─────────────────────────> domain
```

`application/ports` объявляет интерфейсы, которыми пользуются сценарии приложения. Конкретные адаптеры реализуют эти интерфейсы и подключаются в точке сборки. **Domain не импортирует Application, CLI, CSV, репозитории или DI-библиотеку.**

### Структура каталогов

```text
cmd/pos/
└── main.go                         # Сборка приложения через dig и запуск CLI
internal/
├── domain/                         # DDD: сущности, агрегаты, VO, инварианты,
│   ├── student.go                  # фабрика и расчёт итога
│   ├── rubric.go
│   ├── criteria.go
│   ├── student_evaluations.go
│   ├── evaluation.go
│   ├── evaluation_factory.go
│   ├── score_calculator.go
│   └── ...
├── application/                    # Сценарии использования и DTO
│   ├── student_service.go
│   ├── rubric_service.go
│   ├── evaluation_service.go
│   ├── facade.go
│   ├── dto.go
│   └── ports/ports.go              # Интерфейсы хранения и экспорта
└── adapters/
    ├── cli/cli.go                  # Интерактивный консольный интерфейс
    ├── repository/memory.go        # In-memory реализации репозиториев
    └── export/csv.go               # CSV-экспорт
```

**Domain** содержит бизнес-правила, фабрики и доменный сервис; ему не известны способы ввода и сохранения данных. **Application** реализует сценарии через `StudentService`, `RubricService`, `EvaluationService`, использует интерфейсы репозиториев и преобразует доменные объекты в DTO. **Adapters** отвечают за консоль, хранение и CSV. **`cmd/pos/main.go`** — composition root, в котором создаётся контейнер и связываются реализации с портами.

Интерфейсы `StudentRepository`, `RubricRepository`, `StudentEvaluationsRepository` и `ResultExporter` позволяют заменить способ хранения или вывода без переписывания доменной модели. Взаимодействие с ними организовано через внедрение зависимостей, а не через создание конкретных адаптеров внутри сервисов.

## Паттерны проектирования GoF

Применён **один паттерн из каждой группы**, как требуется в задании.

| Группа | Паттерн и реализация | Какую проблему решает |
| --- | --- | --- |
| **Порождающий** | **Factory** — `domain.EvaluationFactory` | Централизует создание `Evaluation`: проверяет, что критерий входит в рубрикатор, и передаёт проверку диапазона балла доменной модели. Не позволяет Application обходить правила создания оценки. |
| **Структурный** | **Facade** — `application.POSFacade` | Предоставляет консольному адаптеру единую точку доступа к сценариям работы со студентами, критериями, оценками и экспортом. CLI не собирает зависимости и не реализует бизнес-сценарии. |
| **Поведенческий** | **Strategy** — `domain.ScoreStrategy`, `WeightedScoreStrategy`, `ScoreCalculator` | Отделяет правило вычисления итога от вызова расчёта. Позволяет заменить алгоритм подсчёта без изменения сценариев приложения и CLI. |

`EvaluationFactory` здесь — специализированная фабрика создания доменного объекта (фабричный подход), без дополнительной иерархии наследования. Этот выбор намеренно сохраняет проект простым: нет искусственных классов или абстракций только ради демонстрации паттерна.

### Dependency Injection

Используется контейнер **`go.uber.org/dig`**. Все зависимости регистрируются в `cmd/pos/main.go`: In-memory репозитории, CSV-экспортёр, генератор ID, фабрика оценок, стратегия подсчёта, `ScoreCalculator`, сервисы Application, `POSFacade` и CLI. Контейнер используется **только на внешней границе приложения**; Domain и Application не зависят от `dig`.

## Демонстрационный сценарий

Для проверки требований задания можно выполнить сквозной сценарий в консоли:

1. Запустить `go run ./cmd/pos`.
2. В **Students → Add student** добавить студента, например Иван Петров, группа `БПИ-101`, `ivan@example.com`.
3. В **Criteria → Add criterion** добавить «Домашняя работа» (`maxScore = 10`, `weight = 0.4`) и «Экзамен» (`maxScore = 10`, `weight = 0.6`).
4. В **Evaluations → Set or replace evaluation** выставить этому студенту `8` за домашнюю работу и `9` за экзамен, используя выданные ID.
5. В **Results → Student result** проверить оценки и итоговый балл **9**.
6. В **Export CSV** создать `results.csv` и открыть ведомость.

Для демонстрации инвариантов стоит дополнительно попробовать ввести оценку `12` при `maxScore = 10` и удалить критерий с уже выставленной оценкой: операции должны быть отклонены. Повторная оценка по тому же критерию заменяет старую; удаление оценки возвращает ячейке состояние `N/A`.

### Экспорт ведомости

Команда **Export CSV** создаёт или перезаписывает файл **`./results.csv`** в текущем рабочем каталоге. Формат содержит столбцы:

```csv
student_id,full_name,group,email,Домашняя работа,Экзамен,final_score
1,Петров Иван,БПИ-101,ivan@example.com,8,9,9
```

Столбцы критериев формируются из актуального рубрикатора. Студенты и критерии сортируются по возрастанию своих ID. Для отсутствующей оценки используется значение `N/A`, а не `0`. CSV формируется средствами стандартной библиотеки Go (`encoding/csv`).

## Ограничения и принятые компромиссы

- **Нет постоянного хранения.** После завершения процесса состояние исчезает; CSV — отчёт, а не механизм восстановления базы.
- **Один общий рубрикатор** для всех студентов. Несколько курсов, пересдачи, история изменений оценок и апелляции не входят в текущий объём.
- **Нет транзакций между репозиториями.** Операции, затрагивающие несколько агрегатов, выполняются последовательно. Решение рассчитано на учебное однопроцессное In-memory приложение.
- **Критерии неизменяемы** после добавления; чтобы изменить параметры, необходимо удалить критерий (при отсутствии связанных оценок) и создать новый.
- **CSV перезаписывается** при каждом экспорте; ошибки записи выводятся пользователю, не завершая работу приложения.

Эти ограничения оставлены осознанно, чтобы сосредоточиться на DDD, инвариантах, границах слоёв и осмысленном применении паттернов без избыточной инфраструктуры.
